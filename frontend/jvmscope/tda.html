Getting started

  • Choose dumps, drop files onto the page, or use Paste. The analysis workspace appears after input is accepted.
  • Sample opens the built-in overview. Browse examples, or the arrow beside Sample, opens named symptom cases and Java 25/26/27 captures. Cards label controlled JVM captures and synthetic scenarios. Selecting an example starts a new session; browsing keeps your current data.
  • Clear cancels pending input, removes the session and resets all filters. Reloading the page also clears the in-memory session. See Sessions and input errors to combine captures.

Sessions and input errors

  • Add to session is the default: files and pastes extend the timeline and thread histories. Choose or drop several files together, including a mix of text and JSON. The snapshot selector identifies each source.
  • Load snapshots in chronological order. The session preserves submission order and snapshot order within each file. Repeated input remains a separate observation; duplicated or reversed timestamps are qualified rather than reordered.
  • A text file may contain several snapshots. Load JSON documents as separate files or pastes; concatenated JSON is not a supported input.
  • Replace session starts a new capture. Invalid input keeps the valid session; valid files in a mixed batch are still accepted. Sample and library examples always start a new session.
  • Empty, invalid or unreadable input opens an error dialog. Partial acceptance opens a warning with source details and the number of snapshots loaded. The message says whether the existing session was kept. You can retry the same file after correcting it.
  • The input status shows the source being analyzed. Additions are queued in submission order; Clear cancels the queue and its analysis.
  • Use sources from the same JVM for thread history. Different reported process IDs split histories. Missing process identity cannot prove that sources came from one JVM; matching uses reported thread IDs, not names alone.

Formats and Java versions

  • Supports HotSpot classic thread dumps from Java 7–27 and Thread.dump_to_file text and JSON from Java 21–27. Regression tests replay controlled captures. Check the generated compatibility matrix for exact builds, distributions and formats; coverage does not certify every vendor, update or platform. OpenJ9 javacores and arbitrary log wrappers are outside this coverage.
  • Java 25–27 file dumps report per-thread states and monitor observations, but no CPU or allocation counters. Unavailable values stay —, not zero. Threads are observed separately, so a lock-graph cycle does not prove a simultaneous deadlock.
  • Java 26+ parking records may report an owner ID. Locks presents it as an observation, without inventing held locks or a confirmed deadlock.
  • Java 27 JSON formatVersion 2 numeric IDs and compatibility v1 string IDs are supported. IDs beyond JavaScript’s safe integer range must be strings to retain their exact value.
  • The server’s Java version is independent of the versions of dumps you can analyze.

Collecting thread dumps

  • For platform threads and JVM-reported deadlocks, use jcmd PID Thread.print -l or jstack -l PID. Replace PID with your application’s process ID and use the matching JDK tools.
  • Check jcmd PID help Thread.print for options supported by that JVM. Where available, jcmd PID Thread.print -e -l adds extended per-thread information. Older JDKs may reject -e; available counters vary by version and format.
  • For virtual and platform threads on Java 21+, use jcmd PID Thread.dump_to_file -format=json /path/to/dump.json, or -format=plain for text. File dumps do not supply CPU/allocation counters.
  • Collect several snapshots from the same JVM to compare behavior. Keep the original timestamps and source order. A single lifetime CPU counter cannot establish that a thread is currently CPU hot.

Snapshot timing and CPU profiles

  • Use Previous snapshot, Next snapshot or the Snapshot selector to navigate. Timestamp labels distinguish valid, missing, duplicated and reversed times. TZ? means no timezone was supplied.
  • The delta summary compares the selected snapshot with its predecessor: state totals and exact identities that are New, Ended or materially Changed. Hover a pill for names. Unresolved identity prevents a definite Ended count.
  • CPU and allocation rates require an exact adjacent thread match, counter deltas and a positive comparable interval. The finer consistent JVM timestamp or thread elapsed-counter interval is used; collector timestamps alone do not establish JVM sampling precision.
  • Details and tooltips explain the interval basis and uncertainty. Rounded measurements are approximate. Conflicting clocks keep counter deltas but suppress rates; coarse estimates marked ≈ do not establish CPU or allocation heat.
  • A thread elapsed counter that decreases beyond its printed resolution contradicts continuity, even when thread and process IDs match. The analyzer starts a new thread series and suppresses CPU/allocation deltas and rates across that boundary. Missing or equally rounded elapsed values do not by themselves break a series.
  • CPU profile adjusts interpretation of measured rates. Balanced uses the defaults, Sensitive surfaces lower sustained rates, and High-throughput requires higher sustained rates. The URL’s cpuProfile parameter retains the selected setting.

Search, filters and charts

  • Search is literal and case-insensitive. It covers identity, state, JVM status, full stack lines (including mounted virtual-thread stacks), scenarios, findings, reasons and evidence metadata.
  • Daemon only selects daemon threads. BLOCKED selects that state; WAITING includes WAITING and TIMED_WAITING. Selecting both state controls combines them. Other filters and search must also match.
  • Deadlocked only selects JVM-confirmed deadlock members. Carrying VT only selects platform threads carrying mounted virtual threads.
  • Click chart slices or legend buttons to filter by state, cumulative CPU time, elapsed time, allocated bytes or allocation rate. The active-filter bar reports the combined visible count and offers a clear action.
  • Charts with unavailable measurements are hidden. A measured zero is data. CPU timelines and allocation rates require suitable adjacent snapshots and counters.
  • The Thread CPU timeline plots CPU percentage only for reliable intervals between exact adjacent observations. Coarse time estimates remain in thread details, marked with ≈, and do not enter the chart or its peak ranking. A point belongs to the interval ending at that snapshot; click it to select the ending snapshot. Hover or select a legend entry to highlight its thread. Its name filter and 5/10/20-series limit are independent of table search. Unsafe comparisons create gaps, not zero activity.
  • Table and chart filters apply across snapshot navigation. Add to session retains chart filters and clears focused-cluster selection. Replace session resets capture-specific chart/cluster controls but keeps generic table filters. Clear resets every filter.

Reading the thread table

  • Each row represents a thread in the selected snapshot. Click anywhere on the row or its Details button. A focused row also opens with Enter or Space.
  • Java state and the header’s JVM status describe different layers and can differ. RUNNABLE alone does not prove CPU consumption; a thread may be waiting in native I/O.
  • Locks held counts distinct reported monitors and ownable synchronizers. — means unavailable; zero means lock information was supplied and no hold was reported. Deadlock marks JVM-confirmed members. Carrier marks a platform thread carrying a mounted virtual thread.
  • Top frame is the first meaningful Java frame found. CPU time is a cumulative per-thread counter, not current CPU usage. Hover for its delta and comparable rate; Details explains the adjacent comparison.
  • Allocated is cumulative per-thread heap allocation, not retained/live heap. Allocation rate uses an exact adjacent counter delta. Neither proves a memory leak.
  • NEW marks a new exact identity. Δ lists changes in state, frame, locks, deadlock, name or measured activity. IDENTITY? means no safe comparison was possible.

Thread details and raw dump

  • Overview, Locks and History occupy the left panel; the central panel keeps the thread dump visible. Each panel scrolls independently. The header identifies the snapshot, source and qualified capture time.
  • Stack is the readable view for classic, text and JSON dumps. It displays reported identity, available state and frames without inventing missing counters. Original or Original JSON preserves the source block’s indentation and blank lines.
  • Colors distinguishes headers, states, locks, JVM frames, common libraries and other frames. Package colors help navigation; they do not prove application ownership or a diagnosis. Original view uses neutral text.
  • Use the stack search box or Ctrl + F for literal, case-insensitive search of the selected view. Switching Stack/Original keeps the query and recalculates matches. Enter and Shift + Enter navigate up to 1000 highlighted matches. Esc clears a query first, then closes Details. Opening another detail view resets search, enables colors and selects Stack.
  • Copy raw thread block always copies the complete original evidence, including whitespace. Display formatting, colors and highlights are excluded. No matched diagnostic rule does not establish that a thread is problem-free.
  • Raw dump opens the selected snapshot in a separate browser tab, with search, thread filters and links back to Details or the dependency map. Snapshot changes, additions, replacement or Clear invalidate and close that tab. If blocked, allow the popup and retry.

Scenarios and findings

  • Badges identify patterns such as Java deadlock, monitor contention, CPU hot, allocation hot, executor idle, carrier thread, selector/event loop, possible starvation and possible livelock.
  • Provenance matters: JVM FACT is reported data; MEASURED is an adjacent-snapshot measurement; MIXED combines measured and inferred evidence; INFERRED interprets state/stack/lock data; HEURISTIC is a possibility that dumps alone cannot prove.
  • Confidence describes rule-match strength, not probability. A deterministic pattern evidence score from 0–100 uses recognized frames, parsed locks/parking metadata and compatible states. A high score never turns an inference into a JVM fact. Hover badges or open Details for the basis and limitations.
  • Synchronization and selector rules use JVM/library frames, parsed lock semantics and state. Application or sample thread names alone do not trigger those rules.
  • CPU hot and Allocation hot require exact adjacent identities and measured rates; lifetime totals alone cannot trigger them. Allocation heat indicates churn, not retained memory, off-heap growth or a proven leak.
  • Possible starvation and Possible livelock remain heuristic. Livelock additionally requires measured current CPU activity; that still does not prove a lack of useful progress.
  • Scenario arrow badges compare first and latest endpoints as growing, shrinking or stable. Details shows intermediate fluctuations and streaks. Series trends require at least two adjacent exactly matched observations; identity ambiguity or gaps produce insufficient data.

Deadlocks and lock contention

  • A JVM-reported Java deadlock opens a dedicated panel. Inspect the full cycle, lock relationships and participating threads. The contention panel also shows owners and waiters when no deadlock is reported.
  • A confirmed hold was listed by the JVM in that snapshot. Observed contention is a reported wait; a likely bottleneck is an observed holder with waiters. These labels do not measure hold duration or prove causality.
  • Across snapshots, lock changes mean appeared, persisted or no longer observed. They do not establish an exact release time.
  • A later possible-livelock pattern may be associated with an earlier exact thread/lock relationship. This heuristic temporal association is an investigation hint, not proof that contention caused livelock.

Thread and lock dependency map

  • Resource map shows waiter → resource → observed owner/initializer. Resources include monitors, ownable synchronizers and class initialization.
  • Thread dependencies collapses the resource hop into waiter → blocker edges. Select or hover an edge for supporting lock IDs and wait kinds.
  • Scope selects connected threads, active contention or confirmed deadlock members. Search accepts names, thread IDs, lock types/IDs and top frames.
  • Wheel to zoom; drag the background to pan or a node to pin it. Use the minimap, Fit, Reflow, fullscreen, neighborhood focus and PNG export for navigation.
  • A graph cycle is a diagnostic signal. It becomes a confirmed deadlock only with the JVM’s explicit deadlock evidence.

Recurring RUNNABLE stack shapes

  • Multiple snapshots reveal recurring RUNNABLE stack shapes. A cluster reports snapshots seen, total occurrences, longest consecutive run and average similarity.
  • Timeline cells show presence across snapshots. Click a non-empty cell to select that snapshot and focus the table on the cluster’s exact members. Other filters still apply; the focus bar shows the remaining count and a clear action.
  • Collapsing the cluster panel keeps its table focus. Changing snapshots clears this snapshot-specific focus.
  • Repeating stacks indicate repeated observations, not continuous execution, CPU consumption or useful progress. Consult measured counters and source evidence.

Similarity, normalization and fingerprints

  • Stacks are normalized before comparison. Volatile differences such as line numbers, generated lambda IDs, native-method markers and hexadecimal-like suffixes are removed or softened.
  • Meaningful frames receive more attention than generic runner, wait and park frames. This reduces matches caused only by shared JVM infrastructure.
  • App frames are non-JDK frame hints and may include third-party libraries. They do not prove application ownership, CPU consumption or useful progress.
  • Fingerprints are compact comparison keys made from normalized frames. Stricter and looser views allow related variants to group together; they are not identities for the complete original stack. Inspect the raw evidence when exact differences matter.

Similarity methods

  • Normalized exact: identical normalized stack shapes.
  • Common tail: strongly shared lower frames, with possible differences above them.
  • Shifted subsequence: a shared contiguous frame block occurs at a different stack depth.
  • Near sequence: many frames share their relative order, with differences or gaps.
  • Frame overlap: shared frames with looser order or structure.
  • Variant merge: a heuristic merge into a broader recurring family; review its variants rather than treating it as an exact match.
  • The method explains how stacks grouped; similarity % describes how closely they matched after normalization. It is a relative algorithm score, not a probability, thread identity or proof of equivalent behavior.

Recurring-stack trends

  • These trends describe observed thread counts for a stack shape, not CPU load or elapsed duration.
  • Growing / Fading: the count at the last observed endpoint is higher/lower than the first. Persistent: present in every snapshot with equal endpoint counts; intermediate counts may vary.
  • Bursty: observed in at most two snapshots when absent from others. Intermittent: present in at least three snapshots with a gap between observations. Stable: a consecutive observed run with equal endpoint counts, absent from some other snapshots.
  • Unavailable: incomplete or incompatible collection coverage/processes prevent safe count comparisons. Missing or partial captures cannot establish that activity decreased.

Side-by-side comparison

  • Open Show side by side in a recurring RUNNABLE cluster. Stack shape 1 is the reference; other shapes are displayed as diffs against it.
  • Neutral lines are unchanged, + means added and − means removed. This compares stack variants, not source-code changes.

Workflow and keyboard tips

  • Read the snapshot summary, then check confirmed deadlocks and contention. Use charts and filters to find threads worth inspecting. Open Details and review evidence and history; with multiple snapshots, compare recurring stacks and measured rates.
  • Ctrl + V pastes a dump when focus is outside a text field. ← / → select adjacent snapshots; Home / End select first/last, when focus is outside form controls and dialogs.
  • In this guide, search matches complete topics containing all entered terms. Use the topic links to jump within the guide. Tab moves between controls and links; Esc closes the guide and returns focus to Help.
  • ?readclipboard requests clipboard input on page open. Browser clipboard permissions still apply.

Privacy and performance

  • Your dumps are parsed and analyzed locally in browser workers. Captures are not uploaded and the tool sends no telemetry. Built-in examples are downloaded from this application’s server, then analyzed locally.
  • Sessions remain in browser memory. Reload or Clear removes them; Clear also cancels pending analysis. Large captures are limited by available browser memory.
  • Copy actions put selected evidence on your clipboard. Raw-dump tabs and exported maps contain the source information you chose to display.
